# Подключение frontend и backend

## Запуск

Из корня репозитория (Python 3.10+):

```powershell
python -m venv .venv
.venv/Scripts/python.exe -m pip install -r backend/requirements.txt
.venv/Scripts/python.exe -m uvicorn backend.api:app --reload --host 127.0.0.1 --port 8000
```

Во втором терминале из корня запустите Backend 2:

```powershell
.venv/Scripts/python.exe -m uvicorn backend.logic:app --reload --host 127.0.0.1 --port 8002
```

В третьем терминале (Node.js 22.18+ или 24+):

```powershell
cd frontend
npm install
Copy-Item .env.example .env.local
npm run dev -- --port 5173
```

Откройте `http://localhost:5173`. Интерактивное описание API: `http://localhost:8000/docs`.
`frontend/api/index.ts` содержит `sendMessage`, `analyzeDocument`, `validateFile` и `ApiError`;
`frontend/api/types.ts` — общий контракт frontend. `DocumentUploader` отправляет первый запрос,
`DocumentResult` — уточняющие вопросы с полученным `conversation_id`.

`VITE_API_URL` задаёт адрес backend (по умолчанию `http://localhost:8000`, без `/chat` или `/analyze`).
После изменения переменной перезапустите Vite; для production пересоберите frontend.
Пустой `VITE_API_URL` отправляет запросы на тот же origin: в этом случае настройте reverse proxy
для `/chat` и `/analyze`.

Backend 2 реализован в `backend/logic.py`, проверка и поиск — в `backend/rules.py`.
Его документация доступна на `http://localhost:8002/docs`, состояние базы — на `/health`.
Состояние API — на `GET /health` (`:8000`). Вопросы без файла уже работают через два
backend-сервиса. Обработка файлов требует OCR (`ml1`) и Extract (`ml2`): они входят
в репозиторий, OCR-модель `PaddleOCR-VL-1.6` едет compose-сервисом `llama`
(`./models/*.gguf`, образ `ghcr.io/ggml-org/llama.cpp:server`).
Для host-режима задайте `PADDLEOCR_VL_URL=http://host.docker.internal:8080/v1/chat/completions`.
Без моделей/сервиса интерфейс покажет ошибку подключения (503/504), а не тестовый ответ.
Адреса можно задать переменными окружения перед запуском uvicorn:

```powershell
$env:ML1_URL = 'http://localhost:8001/ocr'
$env:ML2_URL = 'http://localhost:8003/extract'
$env:BACKEND2_URL = 'http://localhost:8002/answer'
$env:CORS_ORIGINS = 'http://localhost:5173,http://127.0.0.1:5173'
```

Это также значения по умолчанию. Для другого адреса frontend добавьте его origin в `CORS_ORIGINS`
(список через запятую). Файл `.env` backend автоматически не загружает.

## Запросы браузера

### POST /chat — вопрос без нового файла

`Content-Type: application/json`:

```json
{"message": "Какие документы нужны для перевода?", "conversation_id": null}
```

`message` обязателен: до 5000 символов, пробельный вопрос отклоняется.
Для нового обращения `conversation_id` можно не передавать. В продолжении передавайте ID из
предыдущего ответа. Backend добавит историю и ранее распознанный документ, если он был.

### POST /analyze — документ + вопрос

`multipart/form-data` содержит:

- `file` — обязательный JPG/JPEG, PNG или PDF до 10 МиБ;
- `question` — обязательный непустой вопрос, до 5000 символов;
- `document_type` — необязательная подсказка: `study_certificate`, `academic_leave`,
  `internship_certificate`; для автоопределения поле не отправляется;
- `conversation_id` — необязательный ID существующего диалога.

Frontend отправляет исходный файл без сжатия, чтобы не ухудшать распознавание мелкого текста.
`Content-Type` для `FormData` устанавливает браузер вместе с boundary.
Backend проверяет расширение и содержимое, отвергает пустые, повреждённые и защищённые PDF,
а также изображения больше 25 мегапикселей. Конвертация не выполняется.
Новый документ заменяет контекст документа только после успешного ответа Backend 2.

## Ответ обоих маршрутов

Ниже пример формата, а не фактический результат проверки:

```json
{
  "conversation_id": "uuid",
  "answer": "Не хватает даты выдачи. Основание: п. 3.4 Положения.",
  "sources": [{"type": "положение", "reference": "п. 3.4", "url": null}],
  "document": {
    "type": "study_certificate",
    "fields": {"student_name": "Иванов Иван", "issue_date": "не найдено", "stamp": false},
    "ocr_text": "Распознанный текст",
    "coordinates": []
  },
  "verification": {
    "status": "incomplete",
    "missing_fields": ["issue_date"],
    "issues": []
  }
}
```

`document` равен `null`, если документ ещё не присылали. Значения полей могут быть строками,
числами, булевыми значениями, `null`, массивами и объектами JSON. Источники без URL показываются
текстом; кликабельные ссылки допускают только HTTP(S). Координаты сохраняются без изменения;
наложение на изображение потребует согласовать единицы измерения и номер страницы с OCR.

`verification` необязателен в ответе Backend 2; API возвращает `null`, если его нет. Статус
проверки API сам не вычисляет. Наличие распознанного значения не означает, что оно прошло
проверку. Проверка комплектности не равнозначна принятию документа деканатом.

## Контракты внутренних сервисов

1. **ML 1 / OCR** получает multipart-поле `file` с именем, исходными байтами и проверенным MIME.
   Возвращает объект с обязательной строкой `text` и необязательным массивом `coordinates`.
   Дополнительные данные OCR передаются ML 2 без удаления.
2. **ML 2 / Extract** получает JSON `{"ocr_result": {...}}`, а при ручном выборе также
   `"document_type": "study_certificate"`. Возвращает `{"document_type": "...", "fields": {...}}`.
   `fields` обязателен и должен быть объектом. Если тип отсутствует или `null`, API использует
   подсказку пользователя; без подсказки UI показывает «Тип не определён».
3. **Backend 2 / Answer** получает JSON с `question`, `conversation_id`, `document` и `history`.
   `document` имеет формат из ответа выше или `null`. `history` содержит пары
   `{"role": "user" | "assistant", "content": "..."}` (до 20 последних сообщений).
   Возвращает непустой `answer`, массив `sources` и необязательный `verification`.
   `sources` по умолчанию `[]`; каждый источник содержит строки `type`, `reference` и
   необязательный `url`. В `verification` обязательна строка `status`,
   `missing_fields` и `issues` — массивы строк (по умолчанию пустые).

Поиск правил и проверка обязательных полей выполняются Backend 2 в основном запросе
«документ + вопрос». API только проверяет контракт и передаёт результат браузеру.

## Backend 2: стартовые правила и ответы

По умолчанию загружается `backend/data/rules.json`. Настоящее Положение заказчик не предоставил,
поэтому это **официальный источник для хакатона**: стартовые требования из презентации,
перенумерованные как п. 3.1 (справка об обучении), п. 3.2 (академ-отпуск), п. 3.3 (практика).
Ссылки в ответах — `п. 3.1 — Описание кейса`, что проходит формат автопроверки `п. X`.
Шаблон для будущего нормативного документа — `backend/data/university-rules.template.json`.

Три сценария ответа:

- «Документ в порядке»: все настроенные поля есть и их значения прошли проверку;
  `verification.status = complete`. Это проверка комплектности, не решение о приёме.
- «Чего-то не хватает»: отсутствующие поля перечисляются в `missing_fields`,
  неверные даты, противоречивые значения и отсутствие требуемой подписи/печати — в `issues`;
  `status = incomplete`.
- «Ответа нет»: сервис не нашёл достаточных данных по вопросу и предлагает обратиться в деканат.
  Если тип документа неизвестен или требования для него не настроены, `status = unknown`.
  Вопрос без документа возвращает `verification = null`.

Ответ по вопросу и результат комплектности независимы: например, сервис может проверить поля
справки и одновременно сообщить, что о стоимости обучения сведений нет.
В текущей конфигурации поля из презентации считаются обязательными, подпись и печать должны
быть отмечены как присутствующие. Это зафиксировано в `scope_note` как отсутствие настоящего
Положения у заказчика; при появлении документа настройте требования по нему через шаблон.

Поддерживаются aliases типа документа и полей, значения `null`, «не найдено», пустая строка,
логические значения `true`/`false`, «есть»/«нет», «да»/«нет», `1`/`0`.
OCR может передавать значение напрямую или объектом `{"value": "...", "confidence": 0.9}`.
Конфликт разных aliases одного поля даёт замечание. Даты проверяются как реальные календарные
даты в форматах `ДД.ММ.ГГГГ`, `ДД/ММ/ГГГГ`, `ДД-ММ-ГГГГ`, `ГГГГ-ММ-ДД`.

Поиск локальный, по словам вопроса, текстам пунктов и `topics`; внешние LLM/API не используются.
Выводится текст найденных пунктов, а не сгенерированные нормы. Поиск намеренно консервативен:
неизвестные значимые слова дают «Ответа нет». Для новых формулировок расширяйте `topics`.
Короткое уточнение вроде «Почему?» использует предыдущий вопрос пользователя из `history`.
Подпись/печать оцениваются по извлечённым ML-полям: Backend 2 сам не распознаёт изображение
и не подтверждает подлинность документа.

### Как подключить настоящее Положение (когда появится)

Скопируйте `backend/data/university-rules.template.json` в `university-rules.json`, заполните
по реальным пунктам и задайте путь перед запуском Backend 2:

```powershell
$env:RULES_PATH = 'C:/path/to/university-rules.json'
.venv/Scripts/python.exe -m uvicorn backend.logic:app --reload --port 8002
```

- `title` — название источника; `source_type` — `положение` для настоящего Положения;
  `scope_note` — пояснение границ проверки (может быть пустым).
- `clauses` — пункты: уникальный `id`, точный `text`, дополнительные слова поиска в `topics`,
  применимые `document_types` (пустой список означает все типы), необязательный `url`.
- `document_types` — объект, ключи которого совпадают с типами ML. Для каждого задаются
  `label`, `aliases`, `required_fields` и необязательный `date_orders`.
- В `required_fields` каждое поле имеет `name`, `label`, `aliases`, `reference` (ID пункта),
  `kind` (`text`, `date`, `boolean`) и `must_be_true` (только для `boolean`).
  Добавляйте лишь поля, обязательность которых подтверждена источником.
- `date_orders` имеет вид `[{"start": "start_date", "end": "end_date", "reference": "3.1"}]`:
  проверяет, что начало не позже окончания. Оба поля должны иметь `kind = date`.

Пример названия поля: `student_name`, aliases: `name`, `full_name`, `fio`, `ФИО`.
Существующие `document_number` и `internship_period` также имеют aliases для ML-модулей.
Новый автоматически распознанный тип можно добавить в JSON без изменения Python-кода.
Для ручного выбора нового типа дополнительно расширьте список в frontend и API.

База загружается при старте. После редактирования JSON перезапустите Backend 2.
Ошибки JSON, повторяющиеся пункты, неоднозначные aliases и ссылки на отсутствующие пункты
останавливают запуск, чтобы не выполнять проверку по повреждённой конфигурации.
Если путь явно задан через `RULES_PATH`, отсутствие файла также считается ошибкой запуска.

## Ошибки и диалоги

Ошибки возвращаются как `{"detail": "Описание"}`. Для ошибок структуры запроса FastAPI
возвращает `detail` со списком ошибок; frontend обрабатывает оба варианта.

- `400` — пустой вопрос или неподдерживаемый/повреждённый файл;
- `404` — диалог не найден или истёк; начните новое обращение и приложите документ заново;
- `409` — этот диалог уже обрабатывается;
- `413` — файл превышает 10 МиБ;
- `422` — отсутствует обязательное поле, неверный тип или превышена длина вопроса;
- `502` — внутренний сервис вернул HTTP-ошибку, неправильный JSON или нарушил контракт;
- `503` — сервис недоступен или исчерпан лимит диалогов;
- `504` — истекло время ожидания внутреннего сервиса.

Таймаут каждого внутреннего запроса — 60 секунд (`INTERNAL_TIMEOUT`, `backend/api.py`).
Таймаут браузера — 200 секунд для
последовательной цепочки из трёх сервисов. Ошибки не записываются в историю;
автоматических повторных отправок нет. На странице загрузки ошибка сохраняет файл и вопрос.

Диалоги хранятся **в памяти одного процесса**, максимум 1000 диалогов, 1 час бездействия.
Очистка просроченных диалогов выполняется при следующем запросе. Перезапуск теряет историю.
Используйте один worker. Для нескольких workers потребуется общее хранилище и блокировка
диалогов. Регистрация и авторизация в эту интеграцию не входят.

## Проверки

Из корня репозитория:

```powershell
.venv/Scripts/python.exe -m unittest discover -s backend/tests -v
cd frontend
npm test
npm run lint
npm run build
```

Тесты API заменяют внешние сервисы контролируемыми ответами; тесты frontend заменяют `fetch`.
`test_pipeline.py` проверяет совместную работу настоящих API 1 и Backend 2, заменяя только ML.
Тесты проверяют формат запросов, последовательность обработки, ошибки, правила и контекст диалога.
Качество OCR и ответы по реальному Положению требуют отдельной проверки с работающими сервисами.

## results.json для закрытой проверки

```powershell
python -m tools.make_results --input ./closed --output results.json --api-url http://localhost:8000
```

`--input` — папка с файлами и `questions.json` (`[{id, file, question, document_type}]`, `document_type` опционален).
Выход — `[{id, document:{type, fields}, answer, sources, verification, conversation_id}]`, ошибки — `{id, error}`.
