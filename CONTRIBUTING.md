# Правила участия в разработке OnlineDeanery

Добро пожаловать в команду OnlineDeanery!

В этом документе описаны правила работы с Git и GitHub: структура веток, оформление коммитов и порядок отправки Pull Request.

## 1. Структура веток

В проекте используются следующие основные ветки:

- `main` — стабильная версия проекта. В неё попадает только проверенный код.
- `feat/frontend` — общая ветка интеграции изменений фронтенда.
- `feat/backend` — общая ветка интеграции изменений бэкенда.

**Запрещено вносить изменения напрямую в `main`.**

Для каждой задачи необходимо создавать отдельную рабочую ветку. Изменения добавляются в основные ветки проекта через Pull Request.

## 2. Начало работы

Если репозиторий ещё не склонирован на компьютер, выполни:

```bash
git clone https://github.com/ForestX2000/OnlineDeanery.git
cd OnlineDeanery
```

Перед началом задачи необходимо получить последние изменения из соответствующей ветки.

Для разработки фронтенда:

```bash
git switch feat/frontend
git pull origin feat/frontend
git switch -c feature/название-задачи
```

Для разработки бэкенда:

```bash
git switch feat/backend
git pull origin feat/backend
git switch -c feature/название-задачи
```

Вместо `название-задачи` укажи краткое и понятное название, например `login-page`.

## 3. Правила именования веток

Название ветки должно отражать суть задачи.

Используй следующие префиксы:

- `feature/` — добавление новой функциональности.
- `fix/` — исправление ошибок.
- `docs/` — изменение документации.
- `refactor/` — улучшение структуры кода без изменения его поведения.
- `test/` — добавление или изменение тестов.

Примеры:

```text
feature/login-page
feature/student-profile
fix/login-validation
docs/update-readme
refactor/api-service
test/authentication
```

Используй строчные английские буквы и дефисы вместо пробелов.

## 4. Работа над задачей

Во время разработки необходимо:

1. Работать только в своей рабочей ветке.
2. По возможности ограничивать изменения одной конкретной задачей.
3. Соблюдать существующую структуру проекта и стиль кода.
4. Проверять работоспособность изменений перед отправкой.
5. Не добавлять в Git пароли, токены, API-ключи и локальные файлы `.env`.
6. Не добавлять сгенерированные файлы и зависимости, если они не нужны проекту.

Перед коммитом проверь состояние репозитория:

```bash
git status
git diff
```

## 5. Правила оформления коммитов

Сообщения коммитов должны быть короткими, понятными и описывать выполненную работу.

Используй следующие префиксы:

- `feat:` — новая функциональность.
- `fix:` — исправление ошибки.
- `docs:` — документация.
- `refactor:` — рефакторинг кода.
- `test:` — тесты.
- `chore:` — технические задачи и настройки проекта.

Примеры:

```text
feat: add login page
fix: validate user credentials
docs: add contribution guidelines
chore: update gitignore
```

Сообщения коммитов пишутся на английском языке, чтобы придерживаться единого стиля проекта.

## 6. Отправка изменений на GitHub

Добавь изменения в индекс Git:

```bash
git add .
```

Создай коммит:

```bash
git commit -m "feat: describe your change"
```

Отправь свою ветку на GitHub:

```bash
git push -u origin feature/название-задачи
```

Если ветка уже существует на GitHub, обычно достаточно выполнить:

```bash
git push
```

## 7. Создание Pull Request

После отправки ветки на GitHub создай Pull Request.

Для задач фронтенда:

- **Целевая ветка (base):** `feat/frontend`.
- **Рабочая ветка (compare):** твоя ветка с задачей.

Для задач бэкенда:

- **Целевая ветка (base):** `feat/backend`.
- **Рабочая ветка (compare):** твоя ветка с задачей.

Каждый Pull Request должен:

- Иметь понятное название.
- Содержать описание изменений и их цели.
- Указывать, какие проверки были выполнены.
- Проходить проверку перед слиянием.

После проверки изменения объединяются с соответствующей интеграционной веткой.

Когда интеграционная ветка готова и изменения проверены, создаётся отдельный Pull Request в `main`.

## 8. Обновление веток

Перед началом новой задачи необходимо обновить соответствующую интеграционную ветку.

Для фронтенда:

```bash
git switch feat/frontend
git pull origin feat/frontend
```

Для бэкенда:

```bash
git switch feat/backend
git pull origin feat/backend
```

Создавай новую рабочую ветку от актуальной интеграционной ветки, чтобы уменьшить вероятность конфликтов.

## 9. Правила безопасности

- Не вноси изменения напрямую в `main`.
- Не объединяй непроверенный код с `main`.
- Не используй `git push --force` для общих веток.
- Не удаляй общие ветки без согласования с командой.
- Внимательно разрешай конфликты слияния и проверяй результат.
- Согласовывай изменения общей конфигурации проекта с командой.
- Не публикуй секреты и учётные данные в репозитории.

## 10. Общий принцип работы

Стандартный порядок работы над задачей:

1. Получить актуальные изменения.
2. Создать отдельную рабочую ветку.
3. Выполнить задачу и проверить результат.
4. Создать коммит с понятным сообщением.
5. Отправить ветку на GitHub.
6. Создать Pull Request.
7. Пройти проверку и исправить замечания.
8. Объединить изменения с соответствующей интеграционной веткой.
9. После проверки интеграционной ветки — объединить её с `main`.

Спасибо за вклад в развитие OnlineDeanery!
